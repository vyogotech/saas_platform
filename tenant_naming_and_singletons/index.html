    Multi-Tenant Naming Series & Shared Singletons Architecture

    Context: Architectural specification for solving tenant-isolated Naming Series, Sequence Counters, and Global Singletons in saas_platform.

    1. Executive Summary

    In a shared-database, shared-schema multi-tenant Frappe architecture, row-level filtering (tenant_id) resolves data visibility, but global state and shared singletons introduce severe architectural failures:

    1. Naming Series & Counter Collisions (tabSeries):
    2. Counter sequences in tabSeries are shared globally across all tenants.
    3. Number sequence gaps occur when multiple tenants share a prefix (violating tax and audit compliance like GST, VAT, and IFRS).
    4. Document name is the SQL PRIMARY KEY on all DocType tables; two tenants cannot create a document with the same name.
    5. Single DocTypes (tabSingles):
    6. Settings DocTypes (Global Defaults, Accounts Settings, Stock Settings, Selling Settings, etc.) store key-value pairs in a single global table tabSingles.
    7. Changes made by Tenant A overwrite the settings for Tenant B.
    8. Document Naming Settings & Rules:
    9. Prefix customization in the Frappe Desk modifies global DocField options or global Document Naming Rule records.
    10. Fiscal Years, Branding, and Workspaces:
    11. Multiple tenants operate in different tax jurisdictions with varying fiscal cycles, distinct letterheads, and customized workspaces.

    2. Naming Series per Tenant: Deep Dive

    2.1 The Root Problem

    Frappe's naming engine (frappe/model/naming.py) generates document names via make_autoname calling getseries:

    def getseries(key, digits):
    series = DocType("Series")
    current = (frappe.qb.from_(series).where(series.name == key).for_update().select("current")).run()

    if current and current[0][0] is not None:
        frappe.db.sql("UPDATE `tabSeries` SET `current` = `current` + 1 WHERE `name`=%s", (key,))
        current = cint(current) + 1
    else:
        frappe.db.sql("INSERT INTO `tabSeries` (`name`, `current`) VALUES (%s, 1)", (key,))
        current = 1
    return ("%0" + str(digits) + "d") % current

    Default ERPNext series are hardcoded without company or tenant prefixes: - Sales Invoice: ACC-SINV-.YYYY.- - Purchase Invoice: ACC-PINV-.YYYY.- - Sales Order: SO-.YYYY.- - Purchase Order: PO-.YYYY.- - Journal Entry: ACC-JV-.YYYY.-

    The 3 Failure Modes:

    1. Primary Key Collision: If Tenant A and Tenant B both configure INV-.YYYY.-.##### and start from 1, Tenant B's first invoice crashes with: Duplicate entry 'INV-2026-00001' for key 'PRIMARY' because name is the table's unique primary key.
    2. Audit & Tax Non-Compliance (The Number Gap Leak): If both tenants share the default prefix ACC-SINV-.2026.-:
    3. Tenant A issues: ACC-SINV-2026-00001
    4. Tenant B issues: ACC-SINV-2026-00002
    5. Tenant A issues: ACC-SINV-2026-00003 Tenant A now has an unexplained gap (00002 missing). In many jurisdictions (e.g. EU VAT, Indian GST, UK HMRC, Australian ATO), sequential invoice numbering with missing numbers triggers tax audits and fines for suspected off-the-books sales.
    6. Business Volume Information Leak: Tenant A can monitor gaps in their sequential numbering to determine the total transaction volume of all other tenants on the SaaS cluster.

    2.2 Solution Architecture: Composite Tenant-Company Namespace

    In a shared-database multi-tenant cluster, Company abbreviations (Company.abbr) can legitimately be identical across different tenants (e.g. Tenant 1 "Acme Corp" ACM and Tenant 2 "Acme Motors" ACM). If naming series only used Company.abbr, both tenants would collide on tabSeries counters and crash on SQL PRIMARY KEY (tabDocType.name).

    To solve this, saas_platform implements a Composite Tenant-Company Namespace: {tenant_code}-{company_abbr} (e.g. TENANT1-ACM-, TENANT2-ACM-).

    flowchart TD
    A[New Document Save: doc.insert] --> B[Hook: before_naming]
    B --> C{Is Session User Tenant User?}
    C -- No / System --> D[Use Standard Global Series]
    C -- Yes --> E[Resolve Composite Prefix: {tenant_code}-{company_abbr}]
    E --> F[Inject Composite Prefix into doc.naming_series]
    F --> G[make_autoname with Composite Key: TENANT1-ACM-ACC-SINV-.2026.-]
    G --> H[tabSeries Counter updated for TENANT1-ACM-... independently]
    H --> I[Document Name Generated: TENANT1-ACM-ACC-SINV-2026-00001]
    I --> J[before_save Hook: Strip tenant_code for display_number]
    J --> K[display_number = ACM-ACC-SINV-2026-00001]

    Key Architecture & Non-Functional Requirements (NFRs):

    1. Duplicate Company Abbreviation Collision Freedom:
    2. Tenant 1 (tenant_1, ACM) receives series TENANT1-ACM-ACC-SINV-.YYYY.- $\rightarrow$ DB PK TENANT1-ACM-ACC-SINV-2026-00001.
    3. Tenant 2 (tenant_2, ACM) receives series TENANT2-ACM-ACC-SINV-.YYYY.- $\rightarrow$ DB PK TENANT2-ACM-ACC-SINV-2026-00001.
    4. tabSeries counters are partitioned independently (TENANT1-ACM-... vs TENANT2-ACM-...).
    5. Sub-Millisecond In-Memory LRU Caching (@lru_cache(maxsize=1024)):
    6. Abbreviation lookup (get_company_abbr) is memoized in memory. Benchmark tests verify 10,000 lookups complete in $<15\text{ms}$ ($<0.0015\text{ms}$ per call), eliminating database roundtrips during high-throughput document inserts.
    7. Database Concurrency & Row-Lock Partitioning:
    8. In Frappe's getseries(), each series counter in tabSeries is locked using SELECT ... FOR UPDATE.
    9. Because each tenant's series key is prefixed with {tenant_code}-, row-level locks are strictly partitioned. High-volume invoicing in Tenant 1 never blocks or queues Tenant 2.
    10. Column Length Safety:
    11. tabSeries.name is limited to VARCHAR(100), and tabDocType.name is limited to VARCHAR(140).
    12. tenant_code is sanitized to a max of 10 alphanumeric characters, and company_abbr is capped at 8 characters. The composite prefix {tenant_code}-{abbr}- uses $<20$ characters, safely preserving ample headroom.
    13. Customer-Facing Invoice Cleanliness:
    14. The internal database name is TENANT1-ACM-ACC-SINV-2026-00001.
    15. set_display_number runs on before_save (before the initial INSERT), stripping only the {tenant_code}- prefix so display_number is populated as ACM-ACC-SINV-2026-00001 with zero additional SQL UPDATE overhead.
    16. Jinja filter get_clean_display_name strips the tenant code in print formats and PDF exports.
    17. Smart Prefixing & Idempotency:
    18. If a tenant user pre-configures ACM-ACC-SINV-.YYYY.- in Naming Series settings, the hook prepends only {tenant_code}- to prevent duplicated abbreviations (TENANT1-ACM-ACM-...).
    19. If a document is re-saved, the idempotency check detects existing prefixes and avoids re-prefixing.
    20. Production Code Safety:
    21. No mock shims or fallback mock classes exist in production codebase files. All testing harnesses and mocks reside exclusively in test suites.

    3. The "Etc." Problem: Shared Singletons in Frappe

    Beyond naming series, Frappe was built on single-tenant assumptions where numerous system components exist as singletons.

    3.1 Single DocTypes (tabSingles)

    The Problem:

    Single DocTypes (Accounts Settings, Stock Settings, Buying Settings, Selling Settings, Global Defaults, System Settings) are stored in tabSingles: 

    CREATE TABLE `tabSingles` (
    `doctype` varchar(140) NOT NULL,
    `field` varchar(140) NOT NULL,
    `value` text,
    PRIMARY KEY (`doctype`,`field`)
);
    There is only one row per setting for the entire database. If Tenant A modifies default_currency or credit_limit_check, it mutates configuration globally for all tenants.

    The Solutions:

    Approach Implementation Pros Cons
    Approach 1: Company-Level Settings (Recommended for ERPNext) In ERPNext, migrate tenant-specific operational settings to Company DocType custom fields (e.g. Company.default_currency, Company.stock_valuation_method). 100% native; no core table schema hacks; fully supported by ERPNext multi-company features. Limited to settings that can be logically attached to a Company.
    Approach 2: Multi-Tenant tabSingles Partitioning Alter tabSingles to add tenant_id: PRIMARY KEY (doctype, field, tenant_id) and monkey-patch frappe.db.get_single_value and frappe.db.set_single_value. Full isolation across all Single DocTypes transparently. Requires monkey-patching core database accessors; must handle cache keys per tenant in Redis.

    Implementation of Approach 2 (Tenant-Aware tabSingles):

    1. Alter tabSingles Schema Patch: 

      frappe.db.sql("""
    ALTER TABLE `tabSingles`
    DROP PRIMARY KEY,
    ADD COLUMN `tenant_id` VARCHAR(140) DEFAULT 'SYSTEM',
    ADD PRIMARY KEY (`doctype`, `field`, `tenant_id`);
""")

    2. Patch Single Accessors (saas_platform/utils/singles.py): 

      import frappe
from frappe.database.database import Database

_orig_get_single_value = Database.get_single_value

def tenant_aware_get_single_value(self, doctype, fieldname, cache=True):
    tenant_id = frappe.session.get("tenant_id")
    if not tenant_id or tenant_id == "SYSTEM" or frappe.session.user == "Administrator":
        return _orig_get_single_value(self, doctype, fieldname, cache=cache)

    # Check tenant-specific value first
    val = frappe.db.sql("""
        SELECT `value` FROM `tabSingles`
        WHERE `doctype`=%s AND `field`=%s AND `tenant_id`=%s
    """, (doctype, fieldname, tenant_id))

    if val and val[0][0] is not None:
        return val[0][0]

    # Fallback to system default
    return _orig_get_single_value(self, doctype, fieldname, cache=cache)

Database.get_single_value = tenant_aware_get_single_value

    3.2 Fiscal Years (tabFiscal Year)

    Different tenants operate in different tax jurisdictions: - United States: Jan 1 – Dec 31 - India / UK: Apr 1 – Mar 31 - Australia: Jul 1 – Jun 30

    Action: 1. Ensure Fiscal Year has a tenant_id column. 2. In Tenant.after_insert, automatically provision the correct Fiscal Year linked to the tenant's Company based on their country. 3. Remove Fiscal Year from any exempt system doctype lists so permission_query_conditions filters it by tenant.

    3.3 Branding, Letter Heads & Print Formats

    • Letter Head (tabLetter Head): Must be tagged with tenant_id. Tenant A must never view or select Tenant B's corporate letterhead, logo, or tax registration header.
    • Print Format (tabPrint Format): Custom print formats designed by Tenant A must have tenant_id set and isolated.
    • Address & Contact: Already tagged with tenant_id via add_tenant_id_to_all_tables.py and linked to the tenant's Company or Customer.

    3.4 Outgoing Email Accounts & Background Jobs

    • Standard Frappe uses a single default outgoing Email Account.
    • Each tenant should either:
    • Configure their own Email Account (SMTP / SendGrid / Amazon SES credentials) tagged with their tenant_id.
    • Or use the platform's multi-tenant email router where the from_email and reply headers are dynamically set to the tenant's verified domain.

    4. Architectural Summary

    Dimension Challenge SaaS Platform Solution
    Naming Series Counters Shared tabSeries counter leaks volume & causes gaps. Auto-namespace series prefix with Company Abbreviation (ACM-ACC-SINV-.YYYY.-).
    Primary Key Collisions SQL name primary key collisions between tenants. Globally unique prefixed names; optional clean display_number for customer PDFs.
    Single DocTypes (tabSingles) One global setting record per field across all tenants. Company-level field overrides + Tenant-partitioned tabSingles (tenant_id composite key).
    Fiscal Periods Conflicting regional fiscal years. Tenant-isolated Fiscal Year records linked to tenant Company.
    Reports Raw SQL bypasses ORM permissions. AST-based SQL query rewriter (report_tenant_isolation.md).
    Brand Assets Letterheads, templates, print formats shared. Row-level tenant isolation applied to Letter Head and Print Format.
